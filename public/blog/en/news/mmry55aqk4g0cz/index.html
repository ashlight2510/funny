How to Easily Conduct Code Reviews on GitHub

When doing code reviews, it can often be overwhelming to know what to check, right? Especially when working with team members, you might find yourself pondering how to evaluate each other's code and provide feedback. So, this time, I've organized some ways to easily conduct code reviews on GitHub.

1. Requesting a Code Review

Creating a Pull Request (PR)

The start of a code review is, of course, a Pull Request (hereafter referred to as PR). When I upload the code I've worked on as a PR, my team members can easily check it. It's important to write a good title and description when creating a PR; simply stating "I fixed this part" isn't enough. It's better to explain specifically what my intention was in writing this code and what problem it solves. For example, saying "I modified this feature to minimize errors during user login" is more effective.

When I first created a PR, I neglected to provide a thorough explanation, and my team members struggled to understand it. Since then, I've always tried to explain in detail. This part is really important!

2. Creating a Code Review Checklist

What Should I Look For When Reviewing?

Creating a checklist for code reviews is very helpful. For example, checking the readability, performance, and security of the code. By having a checklist, I reduce the chances of missing anything during the review. Sharing the checklist with team members and allowing everyone to add their opinions can make it even more comprehensive.

Additionally, when conducting code reviews, don't forget to provide positive feedback. Compliments like "This part is really clean!" can motivate team members to work even harder.

3. Giving and Receiving Feedback

How Should I Provide Feedback?

Giving feedback is also important. Be cautious when providing negative feedback. Instead of saying, "This is wrong!" it's better to say, "I think this part could be improved like this." I've experienced that when positive feedback is included, team members are more likely to accept it in a good mood.

The same goes for team members receiving feedback. We need to create an environment where they can ask, "I don't understand this part." If we can freely discuss each other's code, it will improve teamwork and the quality of our output.

4. Communication After Review

The Importance of Communication After Review

After the code review is complete, it's a good idea to have a brief meeting with team members. Sharing what went well and what could be improved can greatly help future work. I initially overlooked this process, but after sharing opinions in meetings, I felt that our teamwork became stronger.

Conclusion

Code reviews are not just a process of checking code; they are an important opportunity to strengthen teamwork. By effectively utilizing GitHub's PR feature, along with checklists and positive feedback, I hope you can enjoy the review process. If you have any questions, please leave a comment! I think starting with this would be a good idea.
